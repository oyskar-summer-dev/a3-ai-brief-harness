모델

본체는 그대로 두고 사후 학습만 얹었다
— GLM-5.3 출시

Z.ai가 5.2 본체에 이런 일은 이렇게 하라고 다듬는 훈련, 곧 사후 학습만 얹어 5.3을 냈습니다.

훈련 무대를 코딩 연습문제에서 전문가의 실제 업무로 옮긴 것이 방법입니다.

터미널 작업 평가(Terminal-Bench 3.0)가 4.6에서 28.3으로 뛰어 오픈웨이트 최고라고 밝혔습니다.

자사 코딩 평가에서 5만 토큰으로 31.4%, 12만 쓴 Opus 4.8은 29.5%, Max의 Fable 5는 39.5%입니다.

사이버 역량이 예상보다 빨리 자라 공격 사슬까지 계획하게 됐다고 덧붙였습니다.

캐시가 깨지던 자리 둘이 막혔다
— Claude Code 2.1.235~241 릴리스

게이트웨이를 거치는 세션에서, 그리고 언어 서버가 끊길 때 캐시가 깨지던 문제가 해결됐습니다.

사용 한도 메시지도 세션과 주간 한도가 언제 초기화되는지 알려주도록 바뀌었습니다.

긴 대화형 세션에서 메모리가 계속 늘던 문제와 백그라운드 세션의 자원 사용도 개선됐습니다.

macOS에서는 허용한 폴더 안에 있어도 .env처럼 막아 둔 파일은 읽히지 않고, 이름을 바꿔도 빠져나가지 못합니다.

정해진 시점에 끼어드는 훅이 명령을 비동기로 돌리고 MCP 도구를 직접 부를 수 있게 됐습니다.

도구

Anthropic 컴퓨터 사용, 스킬, 파일 API 출시

자기 앱에 Claude를 붙여 에이전트를 만들 때 쓸 수 있는 컴퓨터 사용, 스킬, 파일 API가 8월 20일 정식 출시되었습니다.

컴퓨터 사용은 화면을 캡처해 사람이 키보드 앞에서 하듯 클릭하고 입력하게 합니다.

모델 호출 한 번에 동작 하나였던 것이 이제 여러 동작을 한 번에 하고, 웹 전용 도구(browser use)도 붙었습니다.

스킬은 반복하는 작업 절차를 묶어 두고 불러 쓰게 하는 자리이며, 코드 실행 샌드박스 안에서 돕니다.

파일은 에이전트가 주고받는 파일을 올려 두는 저장소로, 조직당 1TB에 요청 한도가 5배입니다.

Section 408 — 13
운영

순차로 흐르던 개발 주기를 순환으로
— Anthropic이 낸 플레이북

Anthropic이 AI로 소프트웨어 개발 수명주기를 바꾸는 방법을 담은 플레이북을 냈습니다.

전통적 흐름은 계획·설계·구현·테스트·배포·유지보수를 순차로 흘려 왔습니다.

이 플레이북이 제안하는 방법은 그 여섯 단계를 순환으로 돌리는 것입니다.

마지막 유지보수에서 이슈가 생기면 사람 손 없이 요구사항 문서로 쓰여 첫 단계로 돌아오고, 고친 뒤엔 그 사건의 평가가 붙습니다.

사람은 그 순환을 함께 돌지 않고 위에서 무엇을 시킬지 정합니다.

각 단계에서 실제로 무엇을 하는지는 원문에 담겨 있으니 참고 부탁드립니다.

— Anthropic 사내 운영 사례

Anthropic이 사내 CI/CD 실패 대응을 Slack에서 Claude에게 먼저 맡긴 사례를 냈습니다.

엔지니어가 분기당 내보내는 코드가 2021~2025년의 8배가 됐는데도 품질을 지킨 것은 이 배치 덕이라고 봅니다.

Datadog, Grafana, PagerDuty, GitHub, 쿠버네티스에 연결돼 모니터링과 인프라를 봅니다.

알림이 뜨면 조사용 하위 에이전트를 여럿 동시에 띄워 로그와 대시보드, 커밋을 훑습니다.

초기 분석을 올리기까지 중간값 14분, 가장 빠른 경우 4분이 걸렸다고 밝혔습니다.

상태 보고 서식은 여러 차례 고쳐야 했고 무엇이 읽히는지는 팀마다 다르다고 인정했습니다.

관점

같은 모델인데 23.8점이 갈렸다
— 에이전트의 절반은 하네스다

Claude Code나 Cursor처럼 모델을 감싸 도구를 쥐어 주는 껍데기를 하네스라고 부릅니다.

같은 모델에 같은 과제 106개를 주고 하네스만 바꾸자 52.4에서 76.2로 23.8점이 갈렸습니다.

예전에는 프롬프트로 일일이 시켜야 하던 일을 이제 모델이 알아서 합니다.

그래서 Claude Code는 시스템 프롬프트의 80%를 걷어낼 수 있었습니다.

남은 병목은 모델이 아니라 사람이라, 다음 하네스는 사람이 무엇을 볼지 정하는 쪽으로 간다고 봅니다.

문법과 버그를 읽는 일은 값어치가 낮다
— Honeycomb CTO가 쪼갠 코드 리뷰

Honeycomb 최고기술책임자 채리티 메이저스와 나눈 대담입니다.

지난해 3월만 해도 세대가 갈릴 변화까지는 아니라고 봤다가, 11월에는 일하는 방식을 통째로 바꾼 클라우드에 견주게 됐습니다.

계기는 새 모델이 아니라 Claude Code 같은 도구의 등장이라고 이야기합니다.

그는 코드 리뷰 중 문법과 버그를 읽는 일이 사람이 보태는 값어치 중 가장 낮다고 잘라 말합니다.

대신 읽지 않을 코드가 앞서 만든 범위 안에서 도는지 보는 적합성 테스트를 그 자리에 둡니다.

제품에 넣을지 정하는 대화와 API 설계가 맞는지는 여전히 사람 몫으로 남깁니다.

무엇을 만들지 찾는 쪽으로
— IEEE Spectrum이 짚은 엔지니어의 이동

엔지니어링 매니저를 지낸 Brian Jenney가 IEEE Spectrum에 쓴 글입니다.

명확한 명세를 코드로 옮기는 일을 AI가 빠르게 해내면서 구현 능력의 값이 내려갑니다.

대신 무엇을 해결할지 찾아내는 능력이 남는다고 보고, 그 자리를 프로덕트 엔지니어라 부릅니다.

매니저 시절 침묵하는 쪽보다 근거를 대고 반대하는 쪽을 높게 봤다며, 의견은 근거와 함께 내라고 권합니다.

판단은 취향이 아니라 목표와 데이터로 하라며, 예쁜 리디자인이라도 체류 시간이 떨어졌으면 실패라고 씁니다.
