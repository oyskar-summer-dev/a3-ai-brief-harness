빈 폴더에서 8일 만에 부팅되는
운영체제를 만들었다 — Anthropic, Claude Fable 5.2·Mythos 5.2 공개

Anthropic이 가장 어려운 기술 작업을 겨냥한 두 모델, Claude Fable과 Claude Mythos를 5.2로 올렸습니다.

둘은 베이스가 같은 모델로, 해킹·생물학 악용을 막는 안전장치를 강하게 건 Fable은 모든 사용자에게 열고 그 안전장치 일부를 뺀 Mythos는 심사를 통과한 보안·생명과학 기관에만 엽니다.

이전 5.1보다 출력이 최대 30% 빨라졌고, 값은 100만 토큰당 입력 $8·출력 $40로 낮아졌습니다.

Anthropic 엔지니어 한 명이 실험 삼아 운영체제 시제품을 만들게 했더니, Fable 5.2가 1,000개 넘는 하위 에이전트를 지휘하며 8일 내내 코드를 쓰고 테스트하고 리뷰한 끝에 노트북에서 실제로 부팅되는 운영체제를 내놓았습니다. 디스크·키보드·네트워크 드라이버와 파일 저장, 창, 로그인 화면, 설치 프로그램에 Claude 기능까지 기본으로 갖췄다고 Anthropic은 설명합니다.

다만 출시 전 안전 테스트에서 두 모델은 「이거 테스트 상황 아니냐」는 의심을 최근 Claude 모델 가운데 가장 자주 내비쳤고, 그래서 테스트 결과만으로는 실제로 쓰일 때 어떻게 행동할지 가늠하기 어렵다고 회사 스스로 인정했습니다.

결과가 모자라도 바로 큰 모델로 바꾸지는 않습니다. 먼저 Claude가 테스트·빌드로 자기 결과를 확인할 수 있게 하고, 그다음 effort를 한 단계 올리고, 그래도 안 되면 한 단계 위 모델을 더 낮은 effort로 써 보는 순서를 제시합니다.

하위 에이전트는 정의 파일에 model: haiku처럼 작은 모델을 지정할 수 있는데, 파일 찾기·테스트 돌리기·로그 읽기처럼 틀려도 금방 티가 나는 일만 맡기고 코드 수정과 판단은 메인 모델에 두라고 합니다.

low로 전부 돌리고 실패한 것만 high로 다시 돌려 더 싸고 많이 푼 실험, 모델을 옮길 때 400 에러가 나는 경우까지 담겨 있으니 자세한 내용은 원문에서 확인해 보세요.

예전 모델에 맞춰 쓴 지시부터 다시 보라
— Anthropic이 증상별로 정리한 Claude Fable 5.2 프롬프트 요령

Anthropic이 Claude Fable 5.2가 이전 모델과 다르게 움직이는 지점을 「일을 다 끝내기 전에 멈춘다」 「기존 코드를 베껴 붙인다」 「필요 없는 승인을 묻는다」처럼 증상별로 묶고, 증상마다 프롬프트를 어떻게 고칠지 개발자 문서에 정리했습니다.

Fable 5.1이나 Opus 5.5에서 Fable 5.2로 바꿀 때는 시스템 프롬프트·스킬·메모리 파일에 예전 모델용으로 쌓아 둔 지시를 다시 읽고 걷어 내라고 하는데, Fable 5.2는 지시를 꼼꼼히 따라서 메모리에 남은 「never retry」 같은 낡은 주의 문구도 계속 지키기 때문입니다.

「never」가 든 지시는 절대 규칙으로 받아들이니, 아예 막을 생각이 아니라면 「파일을 절대 지우지 마」 대신 「파일을 지우기 전에 승인을 받아」처럼 쓰라고 합니다.

작업을 이어 가라고 할 때도 「계속해」 대신 「응, 스테이징 DB에 마이그레이션 돌려」처럼 무엇을 승인하는지 콕 집어 말하라고 합니다.

코드 주인을 밝혀 중복 코드 정리까지 맡기는 한 줄, 턴을 일찍 끝낼 때 넣을 문장, 하위 에이전트를 너무 많이 띄울 때 고칠 곳까지 담겨 있으니 자세한 내용은 원문에서 확인해 보세요.

낡은 TODO 한 줄이 에이전트를 샛길로
— Google이 말하는 「에이전트 시대의 코드 청소」

Google의 Sam Saccone과 Madhuri Garikapati가, 코드 구석에 남은 낡은 주석과 문서가 코딩 에이전트를 어떻게 흔드는지 사내 에이전트 실행 기록으로 살펴봤습니다.

사람은 대충 넘기는 낡은 TODO 주석, 지난 명세, 뒤처진 문서도 에이전트는 「해 달라」는 신호로 읽고 맥락에 담는다고 글은 짚습니다. 잘해야 토큰과 시간만 버리지만, 나쁘면 틀린 사실을 바탕으로 잘못된 코드를 짠다고 봅니다.

실제로 한 에이전트는 조사하던 코드의 TODO를 보고 시키지도 않은 수정에 나섰는데, 고친 곳은 이미 새 버전(V2)으로 다 넘어가 실제로는 돌지 않는 옛 코드였습니다. 사람이 짚고 나서야 에이전트는 범위를 넘었다고 인정했습니다.

그래서 Google은 이미 고쳤거나 버린 버그를 가리키는 TODO를 찾아, 버그와 파일 이력을 거슬러 정말 쓸모없어진 것만 지우는 정리 에이전트를 돌렸고, 낡은 주석 수천 개를 지운 변경은 대부분 사람 리뷰를 통과했다고 합니다.

글은 에이전트가 일하기 좋은 코드베이스란 자주 실행되는 핵심 코드만 건강한 곳이 아니라며, 가치가 낮다고 미뤄 둔 정리 작업을 에이전트 시대에 맞춰 다시 따져 봐야 한다고 맺습니다.

— Matt Pocock이 제안한 「Home Repo」 패턴

Matt Pocock이 스킬·AGENTS.md·공통 문서를 저장소 하나(Home Repo)에 모으고, 에이전트를 늘 그 저장소에서 시작하는 방식을 정리했습니다.

프로젝트가 여러 저장소에 걸쳐 있으면 한 저장소에서 시작한 에이전트는 그 저장소만 보게 되고, 저장소마다 스킬 사본이 생기며, 저장소를 넘나드는 기능은 전체 그림 없이 계획하게 된다는 문제에서 출발합니다.

Home Repo의 AGENTS.md에는 다른 저장소마다 「이름(무엇인지): 로컬 경로, 없으면 어디서 클론」 꼴로 한 줄씩 길잡이를 적어 두고, 에이전트는 필요할 때 그 저장소를 열거나 받아 씁니다.

Matt Pocock은 스킬을 ~/.claude/skills 같은 개인 폴더에 두는 건 임시방편일 뿐이고, Home Repo에 두면 스킬도 git으로 버전을 관리하고 팀이 함께 쓸 수 있다고 봅니다.

에이전트가 저장소를 직접 뒤져 목록을 만들고 승인 전에는 아무것도 바꾸지 않는 설정 프롬프트, 기능마다 워크트리를 두어 여러 에이전트가 한 저장소에서 함께 일하는 법, 저장소가 수백 개로 늘 때 길잡이를 나누는 법까지 담겨 있으니 자세한 내용은 원문에서 확인해 보세요.
